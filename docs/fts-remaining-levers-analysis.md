# 距满分还差什么：剩余可优化空间的定量分析

> 目标不变：三类提升之和 ≥150%（平均 50%）。
> 当前（以平台第二次干净基线为准）：build **+22.9%**、tokenize **+21.2%**、query **+69.3%**
> → 和 **113.4%**、平均 37.8% → **75.6 分**。缺口 **+36.6 个百分点**。

## 0. 先看"差值"：每类还要拿多少

| 类别 | 当前 | 若要到 | 需再提升 | 等价于平台绝对值 |
|---|---|---|---|---|
| build | +22.9% | **+45%** | **+22** | 5.028/3.954/2.162 → 3.58/2.82/1.54 s |
| tokenize | +21.2% | **+35%** | **+14** | 0.0529/0.0356 → 0.0468/0.0275 ms |
| query | +69.3% | **+75%** | **+6** | 0.526/0.726/0.602/0.188 → 0.50/0.69/0.57/0.18 ms |
| **合计** | | | **+42** | → 和 **155%**、平均 51.7% → **满分** |

三条都做到就能过线，且留 5 个点余量。下面逐条给出**剩余成本在哪、怎么拿**。

---

## 1. build：+22 个点（最大的一块）

### 1.1 剩余成本分解（本机 `ik_content` = 2.29 s，平台约 3.95 s）

| 组成 | 本机实测 | 占比 | 说明 |
|---|---|---|---|
| **DDL 固定地板** | **0.45~0.55 s** | 20~24% | 1 行数据建索引也要 0.55s。Agent A 已删掉其中 100 ms（checksum 后的 `usleep`），剩余在 4 张 aux 表各自的 PX 建立/sstable 初始化/收尾 |
| **每行写入** | 约 0.96 µs/行 × 1.92 M 行 ≈ **1.84 s** | 76~80% | `fts_index` 960k + `fts_doc_word` 960k + 两张映射表 40k；每行 = 排序比较 + rowkey 编码 + sstable 编码 + 列校验和 |

**结论：build 的对手是"每行 0.96 µs"**，把它降到 0.7 µs 就能拿 −15~18%（≈ +15 个点）；
再把固定地板压 0.2 s 可再拿 +5~7 个点。

### 1.2 可做的三件事（按性价比）

**B-1（优先）：拆解并压缩每行 0.96 µs**
- 位置：`src/storage/ddl/ob_tablet_slice_writer.cpp` 的 `append_row` →
  `ObMacroBlockWriter::append_row`（`src/storage/blocksstable/ob_macro_block_writer.cpp:684`）
  → 微块编码 `ObMicroBlockWriter`；排序在 PX 侧的 sorter（DDL SQL 带 `ORDER BY`）。
- 做法：先给 `append_row` 内部加三段计时（行→store row 编码 / 微块追加 / 宏块 flush 触发），
  以及 sorter 的比较次数与耗时。找出 0.96 µs 里谁占大头：
  - 若**排序比较**占 >40%：DDL 的排序键是 `(word, docid)` 字符串键，比较成本约 20~30 ns × 每行约 20 次比较 ≈ 0.5 µs。
    可评估把"先按 docid 生成、再对整表做一次基数排序/分桶"替换比较排序（字符串首字节分桶可把比较次数降一个量级）；
  - 若**编码**占 >40%：检查每行是否有可省的一次拷贝（`ObDatumRow` → store row 的转换）；
  - 若**列校验和**占 >20%：它不能跳过，但可评估"每批一次"而非"每行一次"（现在是否已经按批？先确认）。

**B-2：继续削固定地板**
- 已知 `TAKE_EFFECT`（enable_index / schema 更新）约 20 ms/表、`GENERATE_DOC_AUX_SCHEMA` 37~52 ms；
- 若收尾阶段的 4 次 schema 变更能合并为 1 次（**只动收尾，不动数据通路**，因此不重蹈 ④ 的并行损失），
  可再省 0.1~0.2 s。
- 注意：④ 的教训是"合并数据通路会牺牲并行度"，**不要**再合并构建通路。

**B-3：不要在 build 上做"合并两次分词"**（已被证否：慢 7.1%）。

## 2. tokenize：+14 个点（需要算法级改造）

### 2.1 剩余成本分解（平台值）

| 组成 | tokenize_ik | tokenize_beng |
|---|---|---|
| 客户端往返 + 语句开销 | **~25 µs**（`select1` 0.0265，**不可优化**） | ~25 µs |
| 服务端 | **~28 µs** | **~10.6 µs** |
| 其中 `segment`（分词） | **16.5 µs**（IK，实测四段：helper 0.2 + map 0.1 + segment 16.5 + json 0.7） | 约 4~5 µs |
| 其余（表达式框架、结果序列化等） | 约 11 µs | 约 5~6 µs |

**关键算式**：`tokenize_beng` 的基线是 42.3 µs，**往返 25 µs 已占 59%** ⇒ 它最多只能做到 +41%
（服务端归零）。当前 +15.8%，理论余量约 +25 个点；`tokenize_ik` 基线 72 µs，服务端归零可到 +65%，
当前 +26.5%，余量约 +38 个点。

### 2.2 可做的两件事（算法级）

**T-1（优先）：IK CJK 逐字从 120 ns/char 降到 50~60 ns/char**
- 现状：`ob_ik_cjk_processor.cpp` 每个字符做两件事——
  ① 遍历已存命中并各自 `match_with_hit`（56 ns/char）；② 从当前字符起 `dict_main_.match()`（64 ns/char）。
  两者都在走**双数组 trie（DATrie）**的逐级跳转。
- 算法替代（三选一，按风险从低到高）：
  1. **首字索引 + 最大匹配**：预建 `first_char → 候选词表（按长度降序）`，对每个起点直接按长度试匹配（memcmp），
     完全绕开 DATrie 的 `base/check` 跳转。中文词长分布集中在 2~4 字，平均比较 2~3 次；
  2. **把 DATrie 的 `base/check` 两数组查找改为单数组 + 位掩码预判**（减少一次随机访存）；
  3. **向量化字符分类**（一次处理 16 个字节判断 ASCII/中文/无用），把分类成本并入段扫描。
- 预期：`segment` 16.5 µs → **9~11 µs**，`tokenize_ik` 0.0529 → **0.045 ms**（+13% 相对，即 +13 个点）。

**T-2：beng 的 ASCII 快路径**
- 现状：beng 服务端约 10.6 µs 处理 115 个 ASCII 字符。
- 做法：ASCII 段用"查表分类 + 直接切分"（不查词典、不做 UTF8 解码），
  把每字符成本压到 ~5 ns；预期服务端 10.6 → **5~6 µs**，`tokenize_beng` 0.0356 → **0.0305 ms**，
  即从 +15.8% 提到 **+28%**（+12 个点）。
- 注意：`tokenize` 类均值是两项的平均，T-1 + T-2 合计约 **+12~13 个点**（不是相加）。

### 2.3 明确做不到的部分
- **客户端往返 25 µs 不可动**（bench 是 3000 条独立 SQL 除总墙钟）；
- 语句层约 11 µs 中，Agent B 已证明约 4.6 µs 是"通用 300 B 结果序列化"、约 2.2 µs 是 JSON 表达式固定开销，
  都不是 tokenize 特有，动它会影响所有查询（风险高、收益小）。

## 3. query：+6 个点（已很高，只做低风险微调）

### 3.1 剩余成本（`query_cn` 平台 0.526 ms）
- 12669 条 posting × 21 ns ≈ **266 µs**（倒排扫描，接近地板）；
- 位图构建 + 位图 emit（已做 count-only）≈ 40~60 µs；
- 语句层 ≈ 37 µs（实测"字面量 vs 预处理"差 0.063 ms 中约 0.037 ms 是解析/计划）；
- 剩余约 150~180 µs 未细分。

### 3.2 可做的两件事
**Q-1：加大倒排扫描批次**
- 现状每批 256 行（`max_batch_size_`）。若存储扫描的**每批固定开销**是 ~1 µs，
  12669/256 = 50 批 ⇒ 50 µs；把批次提到 1024 可省 ~37 µs（约 −7%）。
- 做法：确认 `ObTextRetrievalTokenIter::get_next_batch` 的 capacity 来源，评估提到 1024 的可行性
  （注意 `eval_ctx->max_batch_size_` 与表达式 vector size 的约束）。

**Q-2：位图 emit 的批内提示**
- `set_evaluated_projected` 已提到循环外（上一轮），若还有 per-row 调用可继续外提；
- 门槛 1.5%，无收益就回退。

## 4. 汇总：可拿到的点数与达标路径

| 措施 | 类别增量 | 累计和 | 平均 | 得分 |
|---|---|---|---|---|
| 现状 | — | 113.4 | 37.8 | 75.6 |
| + B-1（每行 0.96→0.7 µs） | build **+15** | 128.4 | 42.8 | 85.6 |
| + T-1（IK 算法级） | tokenize **+9** | 137.4 | 45.8 | 91.6 |
| + T-2（beng ASCII 快路径） | tokenize **+4** | 141.4 | 47.1 | 94.2 |
| + B-2（收尾合并） | build **+6** | 147.4 | 49.1 | 98.2 |
| + Q-1（批次 1024） | query **+3** | 150.4 | 50.1 | **100** |

即：**B-1 是最关键的一项（+15 个点）**，其次是 T-1（+9）、B-2（+6）、T-2（+4）、Q-1（+3）。
五项目标加起来刚好过 150%，没有余量，所以建议**按 B-1 → T-1 → B-2 → T-2 → Q-1 的顺序**做，
每完成一项立刻在平台上验证绝对指标（不要用分数判断，基线侧抖动可达 1.8 倍）。

## 5. 风险与不确定性（如实标注）

1. **B-1 的 0.96 µs/行尚未拆解**——若其中 60% 是 sorter 的字符串比较，则"基数排序/分桶"能拿到大头；
   若大头在 sstable 编码或校验和，可拿的会少一半。**必须先做三段计时再承诺**。
2. **T-1 是算法替换，语义风险最高**：必须用 `tokenize_edge`（14 组）+ 36 形态 dump 逐字节锁定输出，
   包括 token 顺序（哈希桶序）。建议保留旧实现做灰度开关。
3. **Q-1 受 `eval_ctx->max_batch_size_` 约束**，可能改不动。
4. 平台基线侧抖动（1.8 倍）会让单次分数上下浮动 ±15 分，**分数不可作为迭代信号**。

## 6. 不建议再投入的方向（已证否）
- 合并两张分词表的构建（慢 7.1%）；合并两张映射表（前提不成立，收益结构上为 0）；
- 位图归并改手工 k 路（−0.69%）；去 filter guard（+0.14%）；直载写入器的 writer 缓存（+0.08%）；
- 调大 `ob_sql_work_area_percentage`（排序未落盘，5%/30%/60% 无差异）；
- 查询重复计划（计划已缓存，字面量 vs 预处理仅差 8%）。
