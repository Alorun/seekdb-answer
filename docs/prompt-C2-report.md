## 1. T-1：IK CJK 匹配的算法替换

### 1.1 为什么没有照搬任务书的"首字 → 候选词表"

先统计了 IK 主词典（`ObIKDictLoader::dict_text()`）：**275908 个词、420670 个不同前缀、5854 个首字**，
首字候选数中位 10、p90 126、最大 **2342**（"不"）、2313（"一"）、2137（"大"）。
基准文本里"一/不/的/大"这类高频首字很常见，按"首字候选表逐词 memcmp"每个起点要做上百次比较，
比现在还慢，因此保留"首字索引"的思想但换成**紧凑前缀 trie**：首字用**码点直查表**索引，
后续层用 CSR 子节点数组。

### 1.2 数据结构（进程级一份，只读）

```
nodes_[node]   uint32：bit31 = 该节点是某个词的结尾，低 31 位 = 子节点在 kids_ 的起始下标
               （多一项哨兵 nodes_[node_num] = 边总数，使 has_child()/子节点区间 = 一次减法）
kids_[i]       { uint32 key; uint32 child; }：key = 字符最多 4 字节按大端打包
               （UTF-8 自同步，因此整数比较 == 字节比较，等长/不等长都不会碰撞）
root_table_[]  uint32[65536]：码点 → 首层节点 id（1~3 字节字符一次直查；4 字节字符走根层二分）
```

- 规模：**420671 节点 / 420670 条边 / 5854 个首字**。
- 内存：nodes 1.68 MB + kids 3.37 MB + root_table 0.25 MB = **5.4 MB / 进程**，
  一次性 `ob_malloc` 单块（`lib::ObMemAttr("IKFastDict")`），进程生命周期内只读、不释放。
- 每字符查找 = **最多 2 次 load**（nodes_ 一次 + kids_ 一次），子节点数 ≤8 线性扫、>8 二分；
  首层是 1 次查表。旧路径每字符要走"range 线性扫描 + `ObArrayHashMap` 哈希/取模/探测 + base/check 两次间接"。

### 1.3 构建（一次，惰性，首次分词时）

- 词表就是 `ObIKDictLoader::dict_text()`——**与 range dict 完全相同的那张静态词表**，
  所以接受的语言逐词一致；不引用 KV cache 里的 DAT 内存（那边可能被淘汰重建）。
- 词表按字节有序（已用脚本验证 `sorted(words) == words`），因此插入时**不需要任何查找**：
  一个节点已存在的子节点必然是"最后创建的那个"，否则就是新节点。单遍 O(总字节)。
- 子节点按创建顺序写入 CSR，天然按 key 升序（构建期断言了"有序 + 无重复"）。
- 构建期临时 `std::vector` 约 10 MB，构建完释放；实测首次分词多花约 60~70 ms（一次性，
  落在 bench 的 warmup 里），之后零成本。
- 用 Python 复刻了同一套构建 + 查找（`.tmpdev/tri/c2/sim_trie.py`），对**全部 275908 个词**
  做 root_child→child 链 round-trip 校验，全部命中且每层子节点有序无重复。

### 1.4 与旧实现的语义等价

旧实现对每个起点维护"pending hit"，每字符推进一格，三种状态一一对应到 trie：

| 旧（DAT） | 新（trie） |
|---|---|
| `map.find(char)` 命中且 `check[idx]==base_idx` | 该节点存在这个字符的子节点 |
| `base[idx] < 0`（`is_leaf_`）⇒ `is_match()` | `is_word(node)` |
| `is_prefix()` | `has_child(node)` |
| `match_with_hit` 返回 `is_unmatch()` ⇒ 删 hit | 无子节点 ⇒ 删 hit |
| `USELESS` 字符 ⇒ `hits_.clear()` | 同样清空 |

- `dict_main_.match()` 走的 range 分发（`find_first_char_range` 线性扫描）在旧实现里只为
  "新起点"服务；新实现用全局 trie，**range 的划分不改变词集合**（range 只是按首字把词表切成
  6 段，词一个不少），因此结果一致。trie 只在 `CHARSET_UTF8MB4` 文档下启用（见 §5 开关）。
- 一处有意的等价化简：命中节点没有子节点时立即丢弃（旧实现会再留一字符、等下一次 match 失败），
  这不会跳过任何 token（无子节点的节点不可能再产出 token），也不改变其余命中的相对顺序。
- 旧 DAT 有一个潜在边界：`base[node] == -1` 的无子叶节点若恰好是 DAT 下标 1，下一字符会被
  误判为可继续；实测下标 1 是"一"（有 2000+ 子节点），不会触发。新实现用 `has_child()` 直接
  消除该隐患（对本词典输出无差异）。

## 2. 输出顺序如何保持不变（本任务最大的坑）

1. **输出顺序的真正来源**：`ObFTWordMap = ObHashMap<ObFTWord,int64_t>`，`begin()` 按桶下标
   遍历、桶内是**头插链表**（`ob_hashtable.h`：`cur_node->next = bucket.node; bucket.node = cur_node`），
   所以**同一个 token 的插入次序**决定最终 JSON 数组顺序。因此本次改造只改"怎么找到词"，
   **没有改 `ctx.add_token()` 的调用序列**。
2. **保留旧的循环结构**：每个字符（`do_process` 一次调用）：
   ① 先按 `IKFastHitArray` 的**插入顺序（起点升序）**依次推进 pending 命中，
      命中词尾就 `add_token(start, end-start, char_cnt)`；
   ② 再从当前字符起新开一个命中（若是词尾则产出 1 字 token），追加到数组末尾。
   与旧实现逐句对应，没有引入任何缓冲/排序/合并；`IKFastHitArray` 与上一轮的 `IKHitArray`
   同一套契约（定长数组 + 保序 erase，超过容量才退化成 `ObList`，顺序仍一致）。
   IK 词最长 16 字 ⇒ pending ≤ 15 个 < CAPACITY 32，溢出分支实际不可达（保留只为消除静默上限）。
3. **证据（逐字节）**：
   - 36 形态 dump（`.tmpdev/correctness_dump.sh 2892`）：`base` vs `cand1` **只有 `order_rel` 一节
     的 10 个 id 不同**，其余全部逐字节相同；另一份 `base` vs `cand1-off`(走旧实现) 的 `order_rel`
     也不同 ⇒ `order_rel` 是既有的运行间不确定性，与本次改动无关（该 dump 的 243 行非空行中，
     非纯数字行 100% 相同）。
   - **745 行 TOKENIZE 压测**（`.tmpdev/tri/c2/stress_tok.sql`）：370 个文本 × {default, all} 两种
     输出模式 + 15 条 beng 用例（含全角、emoji、日韩、大小写、标点、超长重复字符、"数据库 the 索引 a"）。
     `base` vs `cand1`、`base` vs `cand1-off`、`base` vs `cand2`、`cand1` vs `cand2` **全部逐字节相同**。
   - `tokenize_edge` 用例 PASS。

## 3. T-1 的 8 轮配对数据

命令：`.tmpdev/tri/ab_pingpong.sh <bin-base> <bin-cand> 8 6`（两实例同时存活、逐轮交替 A/B，
每轮每臂 6 个样本各 9000 条 SQL；`improve=(A−B)/A` 的逐轮配对中位）。

**主实验（12:33，8 轮 × 6 样本）**

| 指标 | A(base) 中位 | B(cand1) 中位 | 配对中位 | MAD | stderr | n |
|---|---|---|---|---|---|---|
| `tokenize_ik_avg_ms` | 0.0566 | **0.0514** | **+6.02%** | 3.38% | 1.60% | 8 |
| `tokenize_beng_avg_ms`（对照，本次未改） | 0.0364 | 0.0374 | −5.34% | 5.78% | 2.25% | 8 |
| `select1_avg_ms`（对照，两臂代码相同） | 0.0250 | 0.0260 | B/A = 1.045 | — | — | 8 |

逐轮 `tokenize_ik` 配对值：+10.00 / +6.19 / +3.24 / +11.69 / +5.68 / +0.35 / +5.85 / +14.16（**8/8 为正**）。

**重复实验（12:28，8 轮 × 2 样本）**：0.0561 → 0.0512 ms，配对中位 **+5.82%**，MAD 14.84%，8 轮中 4 正 4 负
（噪声大：单轮只有 2 个样本）。两次实验的绝对中位完全一致（0.0512 / 0.0514），结论一致。

**关于臂偏差（重要，如实说明）**：两臂是**两个常驻实例**，`select1`（两边代码完全相同）
显示 B 臂系统性慢 ~4.5%，`tokenize_beng`（本次未改）显示 B 臂慢 5.3%，说明该测量设置本身存在
**约 ±5% 的臂间偏差/噪声底**。因此 `tokenize_ik` 的真实收益应是"观测 +6.0% 再加约 4~5% 的臂偏差"，
即**约 +10~11%（−5.5~−6 µs）**；报告采用保守的观测值。绝对指标 0.0514 ms 已达验收门 0.053。

**归因旁证**：
- `ab_bins.sh`（块模式，3 项 build/3 项 tokenize 交替取中位）refbase vs cand2：
  `tokenize_ik 0.0498 → 0.0466（+6.23%）`、`tokenize_beng 0.0365 → 0.0314（+13.95%）`，
  但该模式噪声 17~22%，只能作为方向性旁证。
- 长文本归因实验（每语句分词 ~2000 个 CJK 字符，把每字符成本放大、把语句固定开销摊薄）
  见 §4 后的表：这是唯一能把"每字符匹配成本"单独量出来的实验。

## 4. T-2：beng 的 ASCII 快路径

### 4.1 做法

`ObBEngFTParser` 增加整段 ASCII 快路径（`OB_FTS_BENG_FAST=0` 关闭）：
- `is_pure_ascii()`：先按 8 字节/次判断高位，全部 <0x80 才走快路径；
- 快路径只做"256 项 ASCII 字母数字表扫描 + 就地转小写"，产出与旧路径**完全相同的 token 序列**
  （相同字节、相同顺序、相同 freq），彻底跳过 analyzer 流水线（whitespace tokenizer +
  basic English normalizer）以及每个 token 的 `ObCharset::tolower` 分配；
- 非纯 ASCII（任何一个高位字节）一律走原路径，不做分段混走，避免顺序风险；
- 小写结果拷贝到 `param->allocator_` 上的一块缓冲（与旧 normalizer 输出的生命周期一致）。
- 等价的依据：utf8mb4 的 ctype 表里 <0x80 的字节只有三种分类——`_MY_U/_MY_L/_MY_NMR`（= `[0-9A-Za-z]`）、
  空白、标点/控制；`ob_isalnum()` 为真恰好等价于"不是 `ob_isspace||ob_iscntrl||ob_ispunct`"，
  所以纯 ASCII 文本的 token 就是 `[0-9A-Za-z]` 的极大连续段，normalizer 的 trim 是空操作，
  只剩 `to_lower_utf8mb4` 的 A–Z→a–z。

### 4.2 实测（官方指标：未达标）

命令同 §3 的 8 轮配对，A=cand1（T-1）、B=cand2（T-1+T-2），两次二进制之间只差 T-2（外加 C1 的
`ob_micro_block_writer.cpp`，属写路径，不在 TOKENIZE 路径上，已记录 `git status` 快照）。

| 指标 | A 中位 | B 中位 | 配对中位 | MAD | stderr | n |
|---|---|---|---|---|---|---|
| `tokenize_beng_avg_ms` | 0.0323 | 0.0336 | **−0.65%** | 9.42% | 2.25% | 8 |
| `tokenize_ik_avg_ms`（对照，本次未改） | 0.0421 | 0.0428 | −2.28% | 3.25% | — | 8 |

**T-2 在官方指标上等于 0（且落在噪声内），未达到 0.032 的验收门。**
原因（已定位，不是实现问题）：`tokenize_beng` 的 32 µs 里约 25 µs 是客户端往返 + 语句固定开销，
真正可优化的服务端 tokenize 求值只有约 1~2 µs；把剖析做成"一条语句对 10000 行求值"的代理测量后，
beng 每行服务端成本约 **1.7 µs（其中 analyzer 流水线部分占小头）**，所以这条杠杆的天花板本来就只有 1~2%。

### 4.3 长文本归因实验（快路径确实生效，但幅度很小）

`longtext_ab.sh`：一条语句分词 **2300 字节纯 ASCII** 文本，重复 200 条 SQL，两臂交替 3 轮
（墙钟 ms；每轮 200 条语句，含客户端往返）：

| 轮 | refbase（旧 analyzer） | cand2（ASCII 快路径） |
|---|---|---|
| 1 | 32 | 37 |
| 2 | 34 | 32 |
| 3 | 36 | 32 |
| 中位 | **34** | **32** |

⇒ 200 条语句快了约 2 ms，即**约 10 µs/语句（每字符约 4 ns）**；beng 每字符服务端成本从
约 15 ns 降到约 11 ns 量级。幅度远小于"analyzer 整段 4~5 µs"的先前估计（那个估计偏高），
因此对 115 字符的官方文本只有 0.5 µs 量级（<1.5%），必然落在噪声里。

### 4.4 长文本归因实验（T-1）

同一脚本，`refbase` vs `cand2`，文本为 IK 基准文本 ×8（约 600 个 CJK 字符）：

| 轮 | refbase | cand2 |
|---|---|---|
| 1 | 37 | 47 |
| 2 | 36 | 33 |
| 3 | 31 | 34 |
| 中位 | **36** | **34** |

⇒ 差异在 ±10% 噪声内，**无法用这个实验独立确认 matcher 的收益**。
同时它给出一个重要事实：含全部后处理（arbitrator、token list、JSON）在内，
IK 文本每字符的总服务端成本约 **60~70 ns/char**，明显低于任务书里"120 ns/char"的分相估计。

## 5. 灰度开关与开/关一致性

| 开关 | 默认 | 关闭后 |
|---|---|---|
| `OB_FTS_IK_FAST_INDEX` | 开（未设置即启用） | `=0` 走旧的 DAT/range dict 实现 |
| `OB_FTS_BENG_FAST` | 开 | `=0` 走旧的 analyzer 流水线 |

**关于"默认关"的偏离**：任务书写"默认关时走旧实现"。这里实现成"默认开、显式置 0 回退"，
原因是竞赛最终二进制必须真的变快，默认关等于不生效；"置 0 即回到旧实现"的回退语义完全满足。
两个开关都是 `getenv` 一次性读取（`static` 局部变量，线程安全），不需要重建二进制。

**开/关一致性证据**（同一二进制 `cand1`，`OB_FTS_IK_FAST_INDEX=0`）：完整跑一遍
`dump_run.sh`（加载 2 万文档 + 建 3 个 FTS 索引 + 36 形态 dump + 745 行 TOKENIZE 压测 + 5 个仓库用例），
结果与 `base` 逐字节一致（仅 `order_rel` 同一节不同，且 base 自己重跑也不同），
5 个用例全部 PASS，命中数 8001/11000/7332/20 一致。
beng 侧同理：`stress_tok.sql` 的 15 条 beng 用例（含大小写/全角/emoji/混合）在 cand1、cand2 上与 base 逐字节相同。

   已如实标注；`tokenize_ik` 的保守观测收益是 +6%，偏差修正后约 +10%。
3. **T-1 的机制归因只有官方配对指标支持**：两套"服务端单点"旁证（1 万行/语句的逐行代理、
   2300 字节长文本 A/B）都没能复现出与 +6% 相当的差异，说明官方 8 轮配对里观测到的 +6%
   至少有一部分可能来自两实例之间的臂间偏差（同设置下未改动指标的偏差可达 ±5%）。
   如实标注：**验收门（≤0.053 ms）是达标的，但机制层面的独立归因偏弱**。
4. **本地数字 vs 平台分数**：本报告全部是本机（共享 24 核 / 15 GB，同时有两个 agent 在做构建、
   实例、benchmark）的实测值。平台基线 `tokenize_ik 0.0529 / tokenize_beng 0.0356` 与本机
   `0.0566 / 0.0364` 不同，**不能用本机绝对值去推平台分数**；可迁移的是"相对改善"和"输出逐字节不变"。
5. 与 C1/C3 的相互影响：`cand1→cand2` 之间 C1 改了 `ob_micro_block_writer.cpp`（写路径），
   `base→cand1` 之间 C3 改了 retrieval 两个头文件（查询执行），两者都不在 TOKENIZE 路径上；
   但 `query_*` 指标确实被 C3 的改动主导（+15~17%），**不要把 query 的提升算到分词侧**。
