## 2. 口径与可复现性

1. **端到端**用 `.tmpdev/tok_ab2.sh A B rounds pairs reps`（`tok_ab.sh` 的端口/实例隔离副本）：
   两臂各起一个实例，逐对交替跑 `SELECT tokenize(...)`，比较每对相邻的 `(A-B)/A` 中位。
   每 burst 30000 条语句（约 2 s），**4 轮 × 5 对 = 20 对/次**（提示词建议 8 轮；这里用更多
   对数、更长的 burst 提高信噪比，每次仍报告中位 + MAD + stderr）。
2. **本机存在与“实例位置”相关的系统偏差**：同一个二进制分别当 A、B 时，`SELECT 1`
   的配对中位会差 1~4%（本机噪声地板，上一轮报告记录为 1.5~3%）。因此每次判定都
   **正反换臂各跑一次**，并用同一轮的 `select1` 作对照扣除偏差：
   `净收益 ≈ (imp_fwd + bias_sel1_fwd) 与 (imp_rev + bias_sel1_rev)` 的均值。
3. 测量期间**机器上还有另一个 agent 在同时编译/压测同一工作树**：`src/storage/retrieval/*`
   与 `src/observer/composition/*` 在本轮实验期间被并行修改（查询子系统），本报告的数据中
   只有 `tokenize_*`、`build_*`、`select1` 与本改动相关；§8 的 20k 用例里 `query_*` 两项速度
   的变化属于那位 agent 的改动，**不计入本文结论**。这也是本次噪声偏大的主要原因。
4. 步进判定不依赖端到端（分辨率不够），而是用**探针**（`FTS_TOKENIZE_PROF` 环境变量门控、
   默认关闭的一次可预测分支）逐阶段测量；探针在最终二进制中已删除。
5. 复现脚本（`.tmpdev/`，未入库）：`tok_ab2.sh`（端到端 A/B）、`prof_one.sh`（单臂探针）、
   `tok_diff.sh`（TOKENIZE 语料 dump）、`build_equiv.sh`（20k 文档构建 + correctness dump）。

## 3. 实测成本结构（与提示词 §1 的差异）

用探针在**改动前**的二进制上测（`SELECT tokenize(IK_TEXT,'ik')`，91 字，41 个 token）：

| 组成 | 实测 | 说明 |
|---|---|---|
| `parse_param` | 0.63 µs | 与上一轮一致 |
| helper `init` | 0.20 µs | 命中线程局部 memo |
| `ObFTWordMap::create` | 0.10 µs | 127 桶 |
| `ObFTWordMap::reuse()`（清空刚建好的空表） | **3.45 µs** | ⚠️ 提示词未列，是本次最大单项；127 个桶逐个加锁，纯浪费 |
| `segment` 实现体（parser 创建 + token 迭代） | **20.1 µs** | 见下拆分 |
| JSON 建树 `make_token_array_json` | 0.94 µs | |
| `pack_json_res`（tree→bin + 写 datum） | 2.03 µs | |
| **合计（服务端）** | **≈ 27.4 µs** | 与上一轮 25.7 µs 同量级，差异是机器负载 |

`segment` 实现体内部（采样探针，含探针自身的时钟开销，仅看相对比例）：

| 子项 | 实测 |
|---|---|
| IK 逐字处理（`process_one_char` 循环，91 字） | 9.15 µs（≈100 ns/字） |
| 仲裁器 `process` | 2.54 µs |
| `output_result`（第二遍扫描） | 1.52 µs |
| `ObAddWord::process_word` ×41（大小写折叠 + 词表插入） | 4.65 µs（≈113 ns/token） |
| token 出队 + `compound` | 1.20 µs |
| 解析器复用 `segment()` + `free_token_iter` | 0.54 µs |

结论：提示词 §1 把“helper init + map create + 其余三个处理器”归为 ~10 µs，实测其中
**helper init + map create 合计只有 0.30 µs**，其余三个处理器（letter/quantifier/surrogate）
的成本已经摊在“逐字 9.15 µs”里（这正是上一轮位掩码/去虚化换来的）。当前真正的残余是
**逐字词典匹配（9 µs）+ 词表插入（4.7 µs）+ 仲裁器（4 µs）+ 空表清理（3.45 µs）+ JSON（3 µs）**，
其中“空表清理”和“中文 token 折叠”是纯浪费且零风险，因此本次先做这两项。

## 4. 改了什么

全部改动集中在分词热路径：11 个源文件（其中 `ob_ik_hit_array.h` 为新增）+ 2 个用例文件，
源文件 **+166/−43 行**，用例 +23 行。按收益排序：

### 4.1 跳过空词表的 `reuse()`（提示词 §4.2 的简化版，最大单项 −3.4 µs）

`src/storage/fts/ob_fts_parser_helper.cpp`

`ObFTParseHelper::segment(..., clear_words=true)` 无条件调用 `words.reuse()`。
`ObHashMap::clear()` 会遍历全部桶并逐个加写锁——即使表是空的。TOKENIZE 每次
都新建一个 127 桶的空表，于是每次白付 3.45 µs。改为 `clear_words && 0 != words.size()`
才清：空表清空是无操作，**语义完全等价**；非空表（构建路径复用词表时）行为不变。

### 4.2 `hits_` / `count_hits_` 链表 → 定长数组（提示词 §4.1）

`src/storage/fts/dict/ob_ft_dict.h`、新增 `src/storage/fts/ik/ob_ik_hit_array.h`、
`ob_ik_cjk_processor.{h,cpp}`、`ob_ik_quantifier_processor.{h,cpp}`

- 新增 `IKHitArray`：容量 32 的定长数组 + 计数，**按插入顺序**遍历；`erase_at` 用
  “搬移压实”；超过 32 个活跃命中时整体迁移到 `ObList` 继续（不丢 token，顺序不变）。
- `ObDATrieHit` 增加默认构造（数组槽位用）和 `assign_all()`（含 `dict_` 的完整拷贝）。
  原有 `operator=` 故意不拷贝 `dict_`，因此数组内搬移必须走 `assign_all`（提示词已提示此坑）。
- 数组用 `alignas` 的裸缓冲 + placement new，空闲处理器不产生初始化成本。
- 处理器循环从迭代器改为下标遍历，`erase` 与原来 `ObList::erase(value)` 一样是
  “删掉第一个相等的命中”，但不再有“erase 之后 `iter++` 访问已释放节点”的隐患
  （原实现在 arena 下侥幸可用）。

### 4.3 中文 token 跳过无用的大小写折叠（−0.8~1.0 µs）

`src/storage/fts/ob_fts_stop_word.cpp`

`needs_case_conversion()` 原来“含任何非 ASCII 字节”就返回 true，于是**每个中文 token**
都要走 `ObCharset::tolower()`（分配 + 拷贝 + 逐字符扫描），而结果是逐字节不变的。
改为按 UTF-8 解码判断：CJK 统一表意/扩展 A/兼容表意、假名、谚文、CJK 标点、
全角符号（**全角字母除外**）、emoji、扩展 B 以后区段判为“无大小写”；
其余（拉丁/希腊/西里尔/未知/非法编码）仍走原转换路径。判定只影响“是否跳过拷贝”，
不会改变任何字节。

### 4.4 仲裁器跨文档复用（提示词 §4.4 的延伸）

`src/storage/fts/ik/ob_ik_arbitrator.{h,cpp}`、`ob_ik_ft_parser.{h,cpp}`

`ObIKArbitrator` 原本每个 batch 在栈上新建：`ObArenaAllocator` 首次分配要取 8 KB chunk，
`chains_` 每次 `create()` 都要重新分配并清零桶数组。改为 **`ObIKFTParser` 的成员**（解析器
本身已按线程缓存复用），每次 `prepare()` 时 `reuse()`：清空哈希表条目 + 回卷 arena，
**保留桶数组与 arena 页**。桶数按文档长度变化，长度档位不同时仍然 destroy+create，
所以行为与“每次新建”一致。判据：`tokenize_fulltext` 一次调用只跑一个 batch，复用不跨语句。

| 合计 | | **≈ −5 µs**（与端到端 +7~8.7% × ~60 µs 对得上） |

| 尝试 | 结果 | 处理 |
|---|---|---|

## 6. 输出顺序为什么保持不变（本任务最容易踩的坑）

当前输出顺序 = `ObFTWordMap` 的**桶遍历顺序**，既非字典序也非出现顺序。本次：

1. **词表结构、哈希函数、桶数计算、插入顺序一律未动**。本报告 §4.1（跳过空表清理）
   只影响“是否遍历一个空表”，对非空表不变；没有任何桶内结构改动（提示词的 §4.2 未做，见 §7）。
2. `IKHitArray` 按**插入顺序**遍历，`erase_at` 压实保持相对顺序；与 `ObList` 的
   插入顺序一致。溢出时迁移到 list 也是尾部追加，顺序不变。
3. 仲裁器复用只换了 `ObIKArbitrator` 的生命周期，`process()` / `output_result()`
   的算法与遍历顺序完全未变（每次 `prepare()` 前清空 entries）。
4. 大小写折叠只是“跳过逐字节相同的拷贝”，`dst = src` 与 `tolower()` 的结果字节相同
   （已用拉丁/希腊/西里尔/全角/Deseret/扩展 A 等语料验证）。
5. 唯一新增的顺序敏感点：`IKHitArray::at()` 在溢出模式下按索引走 list，仍是插入顺序。

## 7. 未完成部分及原因

| 提示词项 | 预估 | 状态 | 原因 |
|---|---|---|---|
| 提示词 §4.2 词表桶内定长数组 | −1~2 µs | **未做** | 需重写 `ObFTWordMap` 的桶结构（13 个调用点共用该 typedef）。实测词表插入 4.65 µs 里约一半是 `ObFTWord::hash`/`operator==` 的 datum 间接调用，改桶结构并不解决这部分；且顺序必须逐字节复刻（同桶内逆插入序），风险/收益不划算 |

| 提示词 §4.4 处理器位掩码分派 | −1 µs | **部分完成（上一轮）** | 现在是 2 次非虚调用/字；改成位掩码查表只能省一次分支判断 |
| 提示词 §4.5 CJK 字典遍历 | −2~3 µs | **未做** | 逐字 9 µs 里主要是 `ObArrayHashMap::find`（每个字一次哈希查找）。要降下来必须改 trie 状态机或做字符级批量匹配，提示词自己标注“容易改了没收益” |

**为什么没到 0.045/0.030 ms**：改动后服务端约 22 µs（27.4 − 5.3），客户端+语句地板上限约
33 µs，端到端理论下限 ~55 µs；要到 0.045 ms 必须把服务端压到 ~12 µs，即还要再砍 10 µs，
而这 10 µs 只能来自提示词的 §4.2/§4.3/§4.5 三项高风险改动（合计预估 4~7 µs，且不一定能全部拿到）。
本机噪声地板 1.5~4%，单项 1 µs 的改动用端到端根本判定不了，继续叠加会变成“改了但说不清有没有收益”。

## 9. 构建路径是否退化

构建路径（`ObDASDomainUtils::generate_fulltext_word_rows`）与查询路径都走同一个
`ObFTParseHelper::segment()`，而且构建路径同样是**每个文档新建一个 `ObFTWordMap`**
（`ob_das_domain_utils.cpp` 里 `word_map.create(...)` 后传 `clear_words=true`），
所以本报告 §4.1 的“空表跳过清理”在构建路径同样生效，§4.2~4.4 也一样。

两次交替（基准、候选、候选、基准）各起一个 20k 文档实例、建三个 FTS 索引：

| 轮次 | 基准 `build_total` | 候选 `build_total` | 配对差 |
|---|---|---|---|
| 1 | 7.355 s | 7.450 s | −1.3% |
| 2 | 7.026 s | 6.931 s | +1.4% |
| 采用 | — | — | **≈ 0（噪声带内）** |

| 指标（两轮） | 基准 | 候选 |
|---|---|---|
| `build_ik_all_sec` | 3.274 / 3.055 | 3.381 / 3.055 |
| `build_ik_content_sec` | 2.635 / 2.531 | 2.631 / 2.532 |
| `build_beng_en_sec` | 1.433 / 1.429 | 1.428 / 1.335 |
| `build_total_sec` | 7.355 / 7.026 | 7.450 / 6.931 |

结论：**未退化**，也没有可测收益——`build_ik_all` 每个文档约 160 µs，而本改动省下的
“空表清理”按桶数只有零点几微秒，落在本机 ±5% 的抖动里。

（`tokenize_*_avg_ms` 一栏在 `ROUNDS=200` 的缩短口径下被客户端启动开销主导，不用于结论。）

## 10. 线程安全与内存

| 改动 | 作用域 | 说明 |
|---|---|---|
| `IKHitArray` | 每处理器（每文档） | 32×48 B ≈ 1.5 KB，随解析器 arena 分配；空闲槽位不初始化 |
| 仲裁器复用 | 每线程（随 `ObIKFTParser`） | arena 保留峰值页（文档级、几 KB），`reuse()` 回卷；**单个文档的 arena 用量超过 512 KB 时整体 reset**，避免超大文档把内存钉在线程上；桶数变化时重建 |
| 大小写折叠判定 | 无状态 | 纯函数 |
| 空表跳过 | 无状态 | 纯判空 |

全部缓存都是每线程独占，不加锁、不跨线程共享；没有新的全局生命周期。
（探针代码已从最终改动中删除，工作树中不残留 `FTS_TOKENIZE_PROF`。）

## 11. 本地数字与平台分数的区分

- §1 的 +7.0~8.7% / +4.7~7.3% 是**本机端到端**、三次独立 A/B（含两次换臂）的结果；
  `0.0554 ms / 0.0358 ms` 是**按本机比例推算的平台值**，不是平台实测。
- 平台最终分数只有官方跑分能确认；本机在测量期间还有并行负载（另一个 agent 在同一工作树
  编译/压测），实际平台收益可能比本机高（噪声使中位偏低），也可能因为平台机器不同而不同。
- 构建/查询的 `*_sec`、`*_avg_ms` 都是**本机 20k 文档、缩短轮次**的口径，只用于两臂比较，
  不与平台绝对值对齐。
