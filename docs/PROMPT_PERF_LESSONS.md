## 4. 性能失败/负优化原因

### 4.1 直接导致“性能无效/整体 0”

- **ScanPool 关停 use-after-return**：
  - 析构 `++seq_` 唤醒 worker，worker 把旧 `job_` 再执行一次；
  - 旧 lambda 捕获 `executeSelect` 栈上的 `left/right/q8`；
  - 基准结束/关停时异常 → 性能无效。
  - 修复：析构只 stop+notify，worker 执行前检查 stop；ASAN 连续 3 次通过。
- **CPU 绑定**：`sched_setaffinity` 与平台 cgroup/调度冲突，可能超时/异常；已删除。
- **AVX-512 无 XCR0 检查**：CPUID 暴露但 OS 未启用 ZMM 会 SIGILL；已加 `xgetbv & 0xE6`。
- **AVX-512 微基准误判**：短基准认为更快，平台持续负载下降频；必须双内核（q7Dot/q7Dot4）都过门槛。

### 4.2 性能低/下降但有效

- **平台波动**：同一代码出现 4380→3235（−26%）；单次 E 不能当稳定结论。
- **AVX-512 sub/abs 路径**：3688→3579；未验证热路径。
- **4 核查询**：2 核 0.063s，4 核 0.060–0.064s，只有 1.00–1.08×；不合并。
- **flat-row 降 M**：M14.0→13.2MB，但查询慢 20%；净亏。
- **raw vector 去 Huffman**：B4.84→5.69MB，写入不变；净亏。
- **2 线程写**：服务端仍 0.09s；客户端 wall 无改善。
- **响应 batching**：实测无收益，已回退。
- **drop q7 降 M**：M−1.3MB，但查询直接变慢，违反“查询不回退”。

### 4.3 性能结构事实（实测）

- SELECT exec 约 **38µs/q**，其中未过滤 q7 scan **37–38µs**；
- response emit 约 **15µs/q**（管道/驱动，不是 iostream）；
- JSON 组装 0.7µs、JSON 请求解析 2µs、SQL 解析 4.5µs；
- 过滤查询 exec 约12µs；
- 写入服务端约 **78ms/100批**，客户端 wall 约 **283ms**；
- 客户端 JSON/管道约0.2s，服务器无法消除；
- B4.84MB、M14.0MB 已接近该实现稳定值；
- 10k×128 的 q7 扫描已接近2核AVX2上限。
