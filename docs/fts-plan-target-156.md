# 目标上修到 156%（预留 6 个点抗波动）：分配方案

> 口径：综合 = (build + tokenize + query 三类均值) / 3；满分需综合 ≥50%（三类之和 ≥150）。
> **本方案的目标不是 150，而是 156** —— 因为平台基线侧实测出现过 1.84 倍漂移
> （同一份代码两次评测：90.80 分 vs 75.58 分，而 9 个绝对指标全部变好），
> 必须留出 6 个点的余量，才能在基线抖动时仍稳在 100 分。

## 1. 七个措施与分配（合计 +13.5，达成后 156.2%）

> 先说清一件事：边际点是越来越贵的。查询类已经 +74.6%，再快 2% 只值 +0.5 个点；
> 而分词类的 beng 还有 8.2 µs 服务端可压、IK 还剩 16.6 µs 可拆，是唯一能一次拿 4 个点的地方。
> 所以分配重心放在**分词**，构建靠"每行成本"的两次小幅下调，查询只做一次低风险延展。

| # | 措施 | 依据（实测） | 类别增量 | 目标绝对值 |
|---|---|---|---|---|
| **D1** | beng ASCII 快路径（重做，见 §2） | beng 服务端 **8.2 µs** / 115 字符 = 71 ns/char，纯 ASCII 却走通用 UTF8+词典路径 | tokenize **+4.2** | `tokenize_beng` 0.0332 → **0.0297**（+29.8%） |
| **D2** | IK `process_word` 词表插入链 | `groupby_word` **95 ns/token × 41 = 3.9 µs**，占总服务端 23% | tokenize **+1.4** | `tokenize_ik` 0.0454 → **0.0435** |
| **D3** | IK `arbitrator` + charloop 非字典部分 | A2 三块计时：仲裁器 3.4 µs（20%）、charloop 4.6 µs 里字典只占 2.2 | tokenize **+1.7** | `tokenize_ik` → **0.0410** |
| **D4** | IK 再深一步（吃 D2/D3 的剩余余量） | 服务端 16.0 → 14.5 µs（IC 缓存/预取/记账合并） | tokenize **+1.1** | `tokenize_ik` → **0.0395** |
| **D5** | build 每行成本 −3% | 本机 `ik_content` 2.18 s = 地板 0.45 s + 1.92M 行 × **0.86 µs** | build **+1.8** | build 三项各 −3% |
| **D6** | build 再来 −3%（收尾 schema 合并 或 排序键分桶） | C1 已测：收尾 `TAKE_EFFECT` 约 20 ms/表 × 4；排序比较约占每行成本的 40~50% | build **+1.8** | build 三项再 −3% |
| **D7** | query 再 −6% | 上轮"批量消费接口"已拿 +16.5%，说明批次侧仍有固定开销 | query **+1.5** | `query_cn/beng/mixed` 各 −6% |
| | **合计** | | **+13.5** | 和 **156.2%** → 综合 **52.1%** → **100 分，余量 6.2 个点** |

### 打折情景（必须都能守住 100 分）
| 情景 | 和 | 综合 | 余量 | 得分 |
|---|---|---|---|---|
| 全部达成 | 156.2 | 52.1% | 6.2 | 100 |
| D1 只拿到一半（+2.1）、D4 落空 | 151.2 | 50.4% | 1.2 | 100 |

**结论**：全部达成 ⇒ 有 6.2 个点余量；只有"beng 打折 + 两个 build 项全落空"这种多重失败才会掉出 100 分，
而那时应回到 §3 的检查点重新评估，而不是继续叠加。

## 2. 为什么 D1（beng）是最大且最确定的一块

| 事实 | 数值 |
|---|---|
| `tokenize_beng` 官方口径 | 0.0332 ms |
| 减去不可优化的客户端往返（`select1`） | −0.0250 |
| **服务端** | **8.2 µs** |
| 处理内容 | 115 个纯 ASCII 字符、约 20 个 token |
| 每字符成本 | **71 ns**（而 IK 的 CJK 逐字已压到 24 ns 字典跳转 + ~30 ns 其他） |

**结论**：beng 走的是通用路径（UTF8 解码 + 字符分类 + 词缓冲 + 词表插入），
对纯 ASCII 文本有明显浪费。若能到 4.6 µs，`tokenize_beng` → 0.0297（+29.8%）。

**上一轮（C2）试过但失败**：只拿到 −0.65%（落在噪声内）。失败原因是**没有先做侧写**，
凭直觉改了分类路径。本轮要求**先用与 A2 相同的方法量出 beng 的每块耗时**
（字符循环 / 词缓冲 / 词表插入 / 输出），再按数据打最大的一块。

**注意**：`helper.init` 实测只有 0.07 µs、`parse_param` 0.56 µs，
所以 beng 没有"解析器构造"这类隐藏成本，8.2 µs 就是字符循环 + 插入 + 输出。

## 3. 执行顺序与检查点

| 阶段 | 内容 | 完成后预计和 | 是否达标 |
|---|---|---|---|
| 阶段 0 | 提交 A2 + 跑一次平台评测（**必须**，确认 A2 真实收益） | 142.7~146.6 | — |
| 阶段 1 | D1（beng 侧写 + 快路径） | 146.9~150.8 | 接近线 |
| 阶段 2 | D2 + D3（IK 插入链 + 仲裁器） | 149.4~153.3 | **过线** |
| 阶段 3 | D4 + D5（构建 + 查询各再压一点） | 152.4~156.3 | **有余量** |
| 阶段 4 | D7（query 延展）+ D6（build 第二次下调） | **156.2** | **余量 6.2 个点** |

**每阶段结束都要跑一次平台评测**（本地数字只用于判断方向）。若某阶段在平台上没有兑现，
回到该阶段重测，不要在未确认的收益上继续叠加。

## 4. 每个措施的验收门（严格）

| 措施 | 门 | 不达标处理 |
|---|---|---|
| D1 | `tokenize_beng` ≥8%（官方 3000×3 口径），8 轮配对同向 | 回退，记录侧写数据 |
| D2 | `tokenize_ik` ≥3% | 回退 |
| D3 | `tokenize_ik` ≥2% | 回退 |
| D4 | build 三项各 ≥3%（3 块交替中位） | 回退 |
| D5 | 三个 query 指标各 ≥2%（8 轮配对） | 回退 |
| D6 | 任一 ≥2.5% | 否则不采用 |

**通用硬约束**（每条都适用）：
1. `TOKENIZE(...)` 输出**逐字节不变，含 token 顺序**（顺序 = `ObFTWordMap` 桶下标 + 桶内头插链表，
   因此**不得改桶数/哈希函数/`add_token` 调用序列**）；
2. 不改 benchmark 数据/SQL/计时/评分/基线；不跳过 LOB 读取、列校验和；
3. 每步保留灰度开关，可一键回退；
4. 正确性五关：36 形态 dump（仅 `order_rel` 允许差异）、5 个仓库用例
   （`no_score_match`/`tokenize_edge`/`bitmap_dedup`/`bmw_topk_fallback`/`count_only_fast_path`）、
   DDL 专项 14 项、命中数 8001/11000/7332/20、745 行 TOKENIZE 压测逐字节相同。

## 5. 测量纪律（这一条的权重不比任何优化低）

1. **平台评测是唯一裁判**：基线侧漂移可达 1.84 倍，本地与平台也会差 1.8 倍（build）；
2. 本机 `ab_pingpong` 在宿主 load 3.4~4.1 时**已不可用**（A2 记录：同一改动两次测得 −4.93% 与 −6.20%，
   MAD 6.9%~9.2%，且与官方块模式 +10.18% 矛盾）。**优先用单实例交替多采样**（≥15 样本/臂），
   并用 `select1` 与未改指标做臂间偏差校正；
3. 构建类指标用 3 块交替取中位，`build_ik_all` 的 9~16s 离群块作废重跑；
4. 每轮改动只在**一个方向**上动，避免归因不清。

## 6. 明确不做的事（已证否 / 风险过高）

| 方向 | 结论 |
|---|---|
| 合并两张分词表的构建（双 writer） | 实测慢 7.1%（牺牲两个扫描线程的并行度），代码已删 |
| 合并两张映射表 | 前提不成立（源表扫描只走主键不读 LOB；第 2/3 次 ALTER 复用映射表），收益结构上为 0 |
| 位图改手工 k 路归并 | −0.69% |
| 去 `filter_on_demand` guard | +0.14% |
| 直载 writer 指针缓存 | +0.08% |
| `ob_sql_work_area_percentage` 30/60% | 排序未落盘，无差异 |
| 计划缓存优化 | 计划已缓存（字面量 vs 预处理仅差 8%，解析 0.037ms） |
| **`tokenize(常量)` 常量折叠** | **禁止**：IK 词典内容随库变化，tokenize 不是纯函数，折叠会改变语义 |
| 批次 256 → 1024 | 被 `eval_ctx->max_batch_size_` 体系硬约束，改不动 |

## 7. 一句话总结

**先提交 A2 并在平台确认（142.7~146.6），然后按 D1→D2→D3→D4→D5→D6→D7 推进，
把和推到 156.2%，综合 52.1%，即在平台基线再抖 6 个点的情况下仍为 100 分。**
即使 D1 只拿到一半、D4/D6 落空，和仍有 151.2%（综合 50.4%），依然是 100 分。
